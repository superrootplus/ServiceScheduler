# ServiceScheduler

«Планировщик служб Windows» — переносимое WPF-приложение для создания заданий Планировщика заданий, которые запускают, останавливают, перезапускают и принудительно завершают службы Windows.

- Репозиторий: https://github.com/superrootplus/ServiceScheduler
- Текущая версия: **2.1.0**
- Релиз: https://github.com/superrootplus/ServiceScheduler/releases/tag/v2.1.0
- Скачать EXE: https://github.com/superrootplus/ServiceScheduler/releases/download/v2.1.0/ServiceScheduler-2.1.0.exe
- SHA-256 EXE: `2f3696a38263677278aa36cea48610f6c313965890133e2e485fc12bb9df65e1`

## Возможности

- Создание, изменение, удаление, включение и отключение своих заданий в папке `\ServiceManager`.
- Операции: запуск, остановка, перезапуск, жёсткий перезапуск и жёсткая остановка службы.
- Расписания: ежедневно, еженедельно, ежемесячно, однократно, при запуске системы и через интервал.
- Ручной запуск задания и просмотр всех системных заданий без изменения чужих объектов.
- Предупреждение перед принудительным завершением процесса, общего для нескольких служб.
- Свойства конкретного задания: редактирование своих заданий и просмотр системных.
- Открытие штатных свойств конкретной службы через MMC Automation.
- Журнал Windows `ServiceScheduler` с фильтрами по датам и конкретному заданию.
- Поиск служб и скрытие стандартных служб Windows.
- Защищённый исполнитель в `%ProgramData%\ServiceScheduler\ServiceScheduler.exe`, используемый заданиями от имени `SYSTEM`.

## Запуск

Требуются Windows 10/11 или Windows Server с графическим интерфейсом и .NET Framework 4.x. Установка и Python не нужны.

Скачайте `ServiceScheduler-2.1.0.exe` из релиза и запустите его. Приложение само запросит права администратора. Без повышения прав управление службами и заданиями невозможно.

Перед включением жёсткой операции проверьте выбранную службу: `taskkill /F` может привести к потере несохранённых данных и остановить другие службы общего процесса.

## Сборка

Актуальное приложение находится в `wpf/`. Сборка использует только компилятор C# из .NET Framework, внешние NuGet-зависимости не нужны.

```bat
build_wpf.cmd
build_smoke.cmd
build_ui_smoke.cmd
```

Результаты создаются в игнорируемом каталоге `dist`:

- `dist\ServiceScheduler.exe` — приложение;
- `dist\ServiceScheduler.SmokeTests.exe` — функциональные тесты;
- `dist\ServiceScheduler.UiSmokeTests.exe` — UI-тесты.

В Git Bash на Windows команды выглядят так:

```bash
cmd.exe //c build_wpf.cmd
cmd.exe //c build_smoke.cmd
cmd.exe //c build_ui_smoke.cmd
```

Файлы `app.py`, `scheduler_core.py`, `service_core.py` и другие Python-файлы относятся к прежнему варианту проекта и не входят в текущую WPF-сборку.

## Проверка

```bash
./dist/ServiceScheduler.UiSmokeTests.exe
```

UI-тесты можно запускать без повышения прав. Функциональные тесты запускайте от администратора:

```bat
dist\ServiceScheduler.SmokeTests.exe
```

Функциональные тесты создают временные задания в `\ServiceManager` и удаляют их в `finally`. После аварийного прогона проверьте очистку вручную. Не запускайте тесты на машине, где одновременно изменяете задания приложения другим способом.

Базовое состояние релиза 2.1.0 проверено: **38/38 функциональных проверок**, **8/8 UI-проверок**, end-to-end открытие свойств задания и службы.

## Структура

| Путь | Назначение |
|---|---|
| `wpf/Program.cs` | Запуск с повышением прав, GUI и режим `--exec` |
| `wpf/MainWindow.cs` | Главное окно и переходы по ссылкам таблицы |
| `wpf/TaskDialog.cs` | Создание и редактирование своих заданий |
| `wpf/Scheduler.cs` | Task Scheduler 2.0, задания и их метаданные |
| `wpf/ServiceOperations.cs` | Управление службами, WMI и общие процессы |
| `wpf/WindowsEditors.cs` | Свойства конкретной службы через `MMC20.Application` |
| `wpf/ExecutorDeployer.cs` | Защищённая копия исполнителя в `ProgramData` |
| `wpf/Logger.cs`, `wpf/LogWindow.cs` | Журнал Windows и его интерфейс |
| `wpf/SmokeTests.cs` | Функциональные проверки |
| `wpf/UiSmokeTests.cs` | UI-проверки |
| `AGENTS.md` | Правила для бота-разработчика |
| `KIMI_CODE_HANDOFF.md` | Точное состояние и история технических решений |
| `KIMI_CODE_PROMPT.txt` | Короткий промпт для продолжения другим ботом |

## Правила разработки

Другому боту или разработчику сначала нужно прочитать [`AGENTS.md`](AGENTS.md) и [`KIMI_CODE_HANDOFF.md`](KIMI_CODE_HANDOFF.md). Там описаны подтверждённые ограничения Windows, команды проверки и требования к изменениям.

Важно: не восстанавливайте native/MSAA-поиск строк виртуального списка заданий MMC. Он был проверен и не работает. Для заданий используются встроенные свойства, для служб — MMC Automation в STA-потоке.

При изменении поведения обновите код, тесты, встроенную справку и документацию. Не коммитьте `dist`, `backups`, результаты диагностики или временные задания.

## Выпуск релиза

1. Обновите версии в `wpf/Program.cs` и `wpf/AssemblyInfo.cs`, при необходимости — заголовок справки.
2. Пересоберите EXE и выполните все функциональные, UI и end-to-end проверки.
3. Закоммитьте и отправьте исходники в `main`.
4. Создайте аннотированный тег и отправьте его:

   ```bash
   git tag -a vX.Y.Z -m "ServiceScheduler X.Y.Z"
   git push origin vX.Y.Z
   ```

5. Создайте релиз через GitHub CLI и приложите собранный EXE:

   ```bash
   gh release create vX.Y.Z dist/ServiceScheduler.exe \
     --title "ServiceScheduler X.Y.Z" \
     --notes "Описание изменений и результаты проверок"
   ```

6. Проверьте публичную страницу релиза, размер и хеш приложенного файла.
