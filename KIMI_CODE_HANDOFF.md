## 2. Что представляет собой приложение

Актуальная программа — один переносимый WPF EXE с запуском от администратора. Внешних NuGet-зависимостей нет, используется штатный компилятор .NET Framework 4.x.

Программа создаёт задания Windows в `\ServiceManager` для запуска, остановки, перезапуска, жёсткого перезапуска и жёсткой остановки служб. Задания выполняют защищённую копию приложения из `%ProgramData%\ServiceScheduler\ServiceScheduler.exe` от имени `SYSTEM`.

Основной код находится в `wpf/`. Python-файлы в корне относятся к прежнему варианту и не используются текущей сборкой.

## 3. Реализованное поведение

- Создание, редактирование, удаление, включение, отключение и ручной запуск своих заданий.
- Чужие системные задания отображаются только для просмотра и защищены от изменений.
- Поддерживаются все операции служб, включая отдельную жёсткую остановку.
- Перед `taskkill` общего процесса требуется разрешение пользователя; оно сохраняется в задании и повторно проверяется при выполнении.
- Зелёное выделение строки: `#DCFCE7`.
- Верхнее деление часового циферблата возвращает 12 часов.
- Поиск служб работает вместе с флажком «Не показывать стандартные службы Windows».
- Стандартные службы определяются через WMI `PathName` и расположение исполняемого файла в каталоге Windows.
- Справка обновлена и соответствует встроенным свойствам заданий.
- Ссылки задания, службы и результата обрабатываются отдельно.

## 4. Переходы к свойствам — важно

### Задание

`MainWindow.OpenTaskScheduler` не запускает общий Планировщик заданий:

- для своего задания открывается `TaskDialog` с возможностью редактирования;
- для системного задания открывается встроенное окно сведений только для чтения;
- заголовок окна равен точному `TaskInfo.Name`.

End-to-end проверка создала временное задание `\ServiceManager\Spooler — Перезапуск — ежедневно 23-57`, вызвала тот же обработчик `MainWindow.OpenTaskScheduler`, нашла новое окно с точным именем и удалила задание после проверки.

### Служба

`WindowsEditors.OpenService` использует `MMC20.Application` в STA-потоке:

- загружает `services.msc`;
- находит точное отображаемое имя через `View.ListItems`;
- вызывает `View.Select` и `View.DisplaySelectionPropertySheet`;
- ждёт новый диалог `#32770`, в заголовке которого есть точное имя службы;
- устанавливает `UserControl = 1`, чтобы оснастка осталась пользователю.

Подтверждено открытие свойств `Spooler` с заголовком «Диспетчер печати». Не заменяйте проверку простым фактом открытия `services.msc`.

### Результат

`ShowLog(task)` открывает `LogWindow` с выбранным заданием. `MatchesTask` сравнивает `LogEntryInfo.TaskPath` с `TaskInfo.Path`; совместимость по службе сохранена для старых записей. UI-проверка подтверждает фильтрацию чужих записей.

## 5. Что проверено и не работает для заданий MMC

Не повторяйте эти эксперименты без новых технических оснований:

1. `MMC20.Application` находит дерево и папку `ServiceManager`, но `View.ListItems.Count` равен нулю как для библиотеки, так и для папки с заданиями.
2. `ITaskScheduler.Activate` не открывает вложенное задание: путь без начального слеша и с ним возвращает `0x80070003`, одно имя — `0x80070002`.
3. Объект Task Scheduler 2.0 не поддерживает `IScheduledWorkItem`: `QueryInterface` возвращает `E_NOINTERFACE` (`0x80004002`).
4. Виртуальный `SysListView32` не отдаёт элементы через MSAA/UI Automation и не принимает выделение через `LVM_SETITEMSTATE` (`RESULT 0`).
5. Поиск через `LVM_FINDITEM`, чтение через `LVM_GETITEMTEXTW`, ввод имени и выбор индекса клавишами не привели к подтверждённому окну свойств.

Поэтому удалён `NativeListView.cs`, а встроенные свойства являются текущим подтверждённым решением. Не сообщайте пользователю, что открывается штатное окно свойств задания Windows: для заданий используется окно приложения.

## 7. Основные файлы

- `wpf/MainWindow.cs` — таблица и три независимых перехода.
- `wpf/TaskDialog.cs` — свойства и редактирование своего задания, фильтр служб.
- `wpf/WindowsEditors.cs` — только открытие свойств службы через MMC Automation.
- `wpf/Scheduler.cs` — Task Scheduler 2.0 и метаданные своих заданий.
- `wpf/ServiceOperations.cs` — службы, зависимости, WMI и защита общего процесса.
- `wpf/ExecutorDeployer.cs` — защищённый исполнитель и миграция.
- `wpf/Logger.cs`, `wpf/LogWindow.cs` — журнал Windows и фильтры.
- `wpf/SmokeTests.cs` — 38 функциональных проверок.
- `wpf/UiSmokeTests.cs` — 8 UI-проверок.
- `build_wpf.cmd`, `build_smoke.cmd`, `build_ui_smoke.cmd` — полная сборка без внешних пакетов.

## 8. Правила продолжения

- Сначала прочитайте `README.md` и `AGENTS.md`.
- Сохраняйте подтверждённые архитектурные решения и защиту системных заданий.
- Для исправления сначала добавьте тест, воспроизводящий ошибку, и убедитесь, что он падает до исправления.
- Не добавляйте зависимости, если возможности .NET Framework достаточно.
- Диагностику и probes держите только в игнорируемом `dist`; не коммитьте их.
- Не коммитьте логины, пароли, токены, ключи, учётные данные Git или локальные конфигурации с секретами.
- Обновляйте встроенную справку, README и этот handoff при изменении поведения.
- Commit, push и новый релиз выполняйте только по запросу пользователя и после полной проверки.

Известных незакрытых ошибок в базовом состоянии релиза 2.1.0 нет. Следующая задача определяется новым запросом пользователя, а не этим документом.
